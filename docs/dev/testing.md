# Testing PSGopher

What can be checked without a console, and how. Building comes first ([`building.md`](building.md));
what only the console shows is in [`debugging.md`](debugging.md) and [`open-work.md`](open-work.md).

## The host tests

```bash
CC=gcc CXX=g++ ps5/tests/run-host-tests.sh
```

Needs a build first (`build/sdl3-include` from `build-core.sh`, `.deps`, `vendor/gopher64`, the font
headers). Everything runs under AddressSanitizer and UBSan. The runner writes `build/host-tests/`:
**never run two at once**; an agent that needs its own run copies the commands into a scratch folder.

| Test | What it checks |
| --- | --- |
| `test_sdl3` | `ps5/sdl3` against SDL's headers with the PS5 layer's host build: audio accounting and resampling (amplitude, spurious tones, images, frequency ratio, underruns), window and controller answers, events, timers, main-thread calls, text rendering |
| `test_library` | the library's search (which files are games, depth, the title's own folders skipped, each file once, sorting, a share's listing and copy, the kept list), `psgopher.ini` (defaults, round trip, values in range), the shares file (accounts encoded, mount names) |
| `test_menu` | the front end itself, drawn offscreen through the PC's Vulkan (lavapipe: `PSGOPHER_LAVAPIPE_ICD`, default `/opt/lavapipe/lvp_icd.json`) with Dear ImGui's Vulkan backend as on the console, a scripted pad through HOME, RACK, BENCH, the probes, the shares and the keyboard. The core's cheats, covers and descriptions are stood in for (the cover through the real fetch thread, decoder and texture upload). Checks what the screens did and leaves pictures in `build/host-tests/menu-pictures/` |
| `test_quickmenu` | the in-game quick menu over a stand-in frame (a small software rasterizer in place of the interface's overlay): each answer (resume, save and load a probe, reset, quit), one step per press, the stats overlay; pictures in `menu-pictures/quickmenu/` |
| `test_rust_abi` | `ps5/host/rust_abi.c`: its FreeBSD 12 structures against Rust's libc's own offsets (`ps5/tests/rust_abi_offsets`, built for `x86_64-unknown-freebsd`) and the converters against FreeBSD 11 answers |

## The interpreters against the original (lockstep)

Every change to the VR4300 or RSP interpreter must pass this against the unmodified pin before it is
kept ([`workflow.md`](workflow.md) rule 9, [`perf/interpreter-optimisation-plan.md`](perf/interpreter-optimisation-plan.md) §1).

```bash
LOCKSTEP_WORK=/tmp/psgopher-lockstep ps5/tests/run-lockstep.sh                  # self-test, no ROM
ps5/tests/run-lockstep.sh compare --rom PATH --vis 600 [--rsp-every 1] [--state FILE]
ps5/tests/run-lockstep.sh rsp-unit [--trials 4000] [--seed 1]
ps5/tests/run-lockstep.sh trace --core original --rom PATH --vis 300 --out A   # then diff-traces A B
ps5/tests/run-lockstep.sh --candidate DIR ...   # another tree as the candidate (default vendor/gopher64)
```

The script builds two cores for the host with rustc 1.100 (Gopher64's toolchain file) at x86-64-v3,
in the scratch folder (`--work`, outside the repository): the **original** from `git archive` of the
pin, the **candidate** from `vendor/gopher64`. Each core is the tree's `src/device*`, `cheats.rs` and
`savestates.rs`, unchanged, run through its own `device::run_game`, plus `ps5/tests/lockstep/core`:
stubs for the front end (no window, SDL, GPU, audio or input; the speed limiter off; the RTC and RNG
fixed) and parallel-rdp's RDP timing model ported, so DP interrupts arrive as in the real build. The
one change to the copies is a call after each RSP burst, injected into both; `vendor/gopher64` is not
touched, so nothing reaches the PS5 build. Both cores are linked into one binary and run side by side.

- `compare`: a checkpoint at every screen update (PC, GPRs, HI/LO, COP0, COP1, TLB, cache lines,
  the event queue, RSP registers, vector registers, accumulators, flags, divide state, SP registers,
  DMEM, IMEM and its pre-decode, the RCP's registers, PIF RAM, RDRAM in 64 KiB blocks, COUNT) and
  after every K-th RSP burst (all but RDRAM). It stops at the first difference and names it, down
  to the register or the RDRAM block. `--synthetic` runs a test program generated by the harness
  (`harness/src/synth.rs`: CPU ALU, 64-bit, multiply/divide, every load/store width, cached and
  uncached, COP1, branches and likely branches, VI and DP interrupts, an RSP task of every vector
  op class restarted ~60 times a VI, an RDP list). `--state` starts from a Gopher64 savestate
  (`trace --save-state FILE` writes one).
- `rsp-unit`: single RSP instructions on pseudo-random states through both builds' decoders and
  handlers, all outputs compared: every vector funct (with aliasing and every element), every
  LWC2/SWC2 kind over 16 elements × 16 alignments × the DMEM start, middle and end, mtc2 over all
  16 elements × 65536 values, mfc2/cfc2/ctc2, and the scalar unit's ALU, loads, stores and branches.

No ROM is committed or downloaded; no public test suite is on this machine, hence the synthetic
program. What it cannot see: the RDP's output (nothing is rendered, so a game that reads back its
framebuffer runs differently from the console, though the same in both builds), audio, input
(no buttons), wall-clock paths (the speed limiter, the front end's timing), anything in `ps5/host`,
the save-type table (header or `--save-types`, else EEPROM 4K + SRAM), and changes outside the
copied files (`Cargo.toml` profiles, `build.rs`, `psgopher.rs`). It localises a divergence to a
VI or an RSP burst, not to an instruction. A candidate that renames a field the harness reads
(`harness/src/glue.rs`) stops it compiling: adapt the glue, not the comparison.

## Looking at the interface

The pictures are the review of any interface change: open the ones the change touches
(`1-home.png`, `3-rack.png`, `5-bench.png`, `13-home-probes.png`, the quick menu's) and compare with
the design, `ps5/art/live-board.html` (open it in a browser). A new screen or state gets a step in
`test_menu.cpp` that draws it.

## The renderer's accuracy

parallel-rdp's conformance suites (`rdp-conformance`, `vi-conformance`) compare the GPU's RDRAM and
TMEM with angrylion-rdp-plus's byte for byte; results and how they were built are in
[`compatibility.md`](compatibility.md#renderer-accuracy-parallel-rdps-conformance-suites).

[`../frontend-audit/`](../frontend-audit/MASTER_PLAN.md) holds the audit of the front end: the
